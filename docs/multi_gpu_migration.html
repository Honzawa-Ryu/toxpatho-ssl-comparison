00

前提・現状認識

このコードベースは「将来のマルチGPU化」を見据えた設計が既にされている。 lib/trainer/distributed.py を中心に拡張ポイントが切り出されており、 entry.py / model.py からの呼び出し配線も済んでいる。

ただし実装自体は全て no-op で、シングルGPU専用のまま。 また、SSL手法側（Barlow Twins / SwAV / DINO）にはDDP対応コードが 書かれてはいるが、コメントアウトされて無効化されている箇所がある。

01

分散学習ロジック本体

lib/trainer/

未実装 コードが存在しない 要修正 既存コードの変更が必要
ファイル現状必要な変更
distributed.py 未実装 setup()/teardown()/rank()/world_size()/wrap() が全て no-op（rank()=0, world_size()=1 固定）。torch.distributed.init_process_group の呼び出し、環境変数（RANK/WORLD_SIZE/LOCAL_RANK）読み取り、DistributedDataParallel ラップを実装する。呼び出し口は既に配線済みなので、ここを実装するだけで多くが繋がる。
context.py:90 要修正 device = torch.device('cuda:0' if ...) が固定。local_rank に応じた cuda:{local_rank} への変更が必須（さもないと全プロセスがGPU0を奪い合う）。
entry.py 要修正 _run() 内の wandb.init(...) にrank0ガードなし。distributed.is_main_process()（定義済み・未使用）でガードしないと、重複run・重複ログが発生する。
loop.py 要修正 torch.save(state, ...)、LOGGER.logger.info(...)、run.log(...) が全プロセス実行前提。チェックポイント書き込み・ログ・wandb.logをrank0限定にしないと、複数プロセスが同じファイルに競合書き込みする。
data.py 未実装 WebDatasetのshardをk-fold分割しているだけで、split_by_node/split_by_worker（webdatasetが提供）が未実装（コメントで明言済み）。今のままだと各GPUプロセスが同じシャードを重複して読む。.with_epoch(...) のepoch長計算もworld_sizeを考慮していないため再設計が必要。
optim.py 未実装 world_sizeに応じた学習率スケーリング（linear scaling rule等）が未実装（コメントで明言済み）。global batch sizeが変わるSSL手法（特にBarlow Twins/SwAV/SimCLR）は要調整。

所見

データローダーが shard を rank ごとに分割していない状態でマルチGPU化すると、 学習効率が上がらないどころか、各GPUが完全に同じデータを重複して読むだけの 構成になる。分散化の中でも優先度が高い。

02

SSL手法側のDDP対応

lib/sslmodel/models/

見落としやすいポイント。GPUを増やしても、手法によっては 各GPU内のミニバッチだけで統計量を計算すると数学的に誤った損失になるため、 個別対応が必要。

無効化 実装はあるがコメントアウト済み 未実装 要検討
ファイル現状内容
barlowtwins.py:126-132 無効化 cross-correlation行列を全GPUでall_reduceするコードが実装済みだがまるごとコメントアウト（#if self.gather_distributed...）。有効化しないと、各GPUが自分のローカルバッチだけでcross-correlationを計算する＝実効バッチサイズが増えない。
swav.py:156-176 無効化 Sinkhorn-Knopp反復のall_gather/all_reduceも同様にコメントアウト。SwAVはプロトタイプ割当がバッチ全体の分布に依存するため、GPU間gatherなしだと崩壊しやすい。
dino.py:96-99
(update_center)		 未実装 teacher出力のcenterをローカルバッチの平均だけで更新している。マルチGPUでは全GPUのteacher出力をall_reduceしてcenterを揃える必要がある。
trainer/model.py
(BatchNorm)		 要検討 ResNet50/DenseNet121バックボーンや各種ProjectionHeadが nn.BatchNorm1d/2d を使用。DDPでは各GPUのローカルバッチでBN統計が計算され、有効バッチサイズが小さいままになる（SimCLR系は特に影響大）。SyncBatchNorm.convert_sync_batchnorm の適用を検討。

所見

Barlow Twins / SwAV は「GPU間で正しい統計を取らないと収束の意味が変わる」手法。 コメントアウトされたコードが再度書かれたことがあるということは、 過去に一度着手されて途中で止まった形跡とも読める。有効化前に、当時止めた理由が 残っていないか確認するとよい。

ファイル現状必要な変更

run_slurm.sh
(RUN_COMMAND)		 要修正 単一プロセス起動（python ...）前提。1ノード内マルチGPUなら torchrun --standalone --nproc_per_node=N、複数ノードなら srun ... torchrun --rdzv_backend=c10d --rdzv_endpoint=$MASTER_ADDR:$MASTER_PORT --nnodes=$SLURM_NNODES --nproc_per_node=N へ変更。MASTER_ADDR（scontrol show hostnames 等で先頭ノードを解決）や空きポートの決定ロジックも追加が要る。

data.py / run_slurm.sh

exp_common.sh
(exp_resolve_partition)		 要確認 パーティション自動判定が実行時間のみに基づく（GPU数は考慮外）。対象スパコンのパーティション体系がGPU数で分かれている場合は拡張が必要。
PBS(Miyabi)投入 要確認 README/USAGE記載の通り、runx（ジョブ投入）は現状Slurm専用。対象スパコンがPBS系（Miyabiなど）でマルチGPU投入も自前ツールでやりたい場合、投入側の拡張が別途必要（現状PBSはキャンセル・監視のみ対応）。
04

コンテナ・依存関係

ファイル現状備考
env/env.def 要確認 nvidia/cuda:12.8.1-cudnn-devel-ubuntu24.04 ベース。NCCLはpip版torch wheelに同梱されるため単一ノード内マルチGPUは概ね問題ないはず。マルチノードでInfiniBand/専用インターコネクトを使う環境では、サイト固有のNCCLプラグイン（libibverbs、UCX、ベンダー製OFIプラグイン等）がコンテナに入っているか要確認。対象スパコン側の推奨NCCL設定に合わせて再ビルドが必要になる可能性が高い。
pyproject.toml 概ね良好 torch自体はcu130ホイールで問題なし。追加のマルチノード通信ライブラリ（nccl-testsでの動作確認等）が要る場合は別途検討。
05

運用・検証観点

  • wandb/Slack通知の重複防止（rank0限定化、§01と連動）
  • WebDatasetのシャード数がGPU数（world_size）に対して十分か（data/shards は現状20シャード → GPU数がこれを超えると空プロセスが出る）
  • 有効バッチサイズが変わることによる、Goal.yaml 記載の「原論文設定準拠」方針とのすり合わせ（LRだけでなくbatch/epoch設計全体の再検討）
  • まずは1ノード内マルチGPU（DDP, torchrun --standalone）で動作・収束を検証し、その後マルチノードへ拡張する段階的アプローチを推奨
  • Makefile: test/tests/ にDDPのsmokeテスト追加、scripts/preflight_check.py にGPU数・torchrun起動設定の整合性チェック追加を検討
06

推奨の着手順

依存関係上、この順で進めるのが自然。

  1. 分散基盤の実装
    lib/trainer/distributed.py 実装 ＋ rank0ガード（entry.py / loop.py）
  2. データ分割
    lib/trainer/data.py のシャードのrank分割
  3. SSL手法の統計量修正
    SSL手法別のgather/all_reduce有効化（barlowtwins.py / swav.py / dino.py）
  4. 単一ノード内マルチGPU起動
    templates/run_slurm.sh / scripts/slurm_entry.sh のマルチGPU起動対応（torchrun --standalone から）
  5. マルチノード対応
    srun + torchrun の rendezvous、コンテナ側ネットワーク設定
